# MollyCloud 桌面版更新与 R2 发布

Windows 桌面版每次启动会静默请求 `https://desktop.veriolink.com/latest.json`；Mac 按架构读取 `latest-macos-aarch64.json` / `latest-macos-x86_64.json`。检查不依赖账户登录；只有清单中的 SemVer 高于本地版本时，登录后的控制台才显示更新说明弹窗和顶部“软件可更新”入口。网络失败、没有清单或没有更高版本时继续正常启动。

当前实现采用**自动检测、用户确认下载和安装**：点击“下载更新”会在系统浏览器打开更新域名上的固定版本 NSIS（Windows）或 DMG（Mac）。客户端不静默运行外部安装器。更新清单必须含固定版本文件名、大小与 SHA-256；它们可供人工核对，但同一清单内的哈希不能代替代码签名。将来若改为应用内一键下载安装，必须先配置 Tauri Updater 签名公钥、保护私钥并发布 `.sig`，再启用签名验证与安装流程，不能直接执行当前未签名的包。

## R2 地址和访问边界

存储桶为 `mollycloud-desktop`。账户的 `r2.cloudflarestorage.com` 地址是 S3 API 端点，用于授权上传，**不是供客户端匿名读取安装包的地址**。客户端只访问 `desktop.veriolink.com`，它需要在 R2 存储桶的公共访问设置中绑定为自定义域。2026-09-23 检查时 `latest.json` 返回 404：发布前须在 Cloudflare 控制台确认域名确实指向这个存储桶，并验证公共 GET/HEAD。

访问密钥、Secret Access Key 或 API Token 均不得写入仓库、安装包、发布清单或日志。`app/scripts/publish-desktop-release.mjs` 使用 Wrangler 发布，读取发布者本机环境中的 `CLOUDFLARE_API_TOKEN`；单独的 R2 S3 Access Key ID 不能用作 Wrangler 的 API Token。如改用 S3 API 上传，则同时需要 Access Key ID 和 Secret Access Key，客户端仍不使用任何上传凭据。

## 发布步骤

下一个版本例如 `0.1.6`：先更新 `app/package.json`、`app/src-tauri/Cargo.toml`、`app/src-tauri/tauri.conf.json` 等版本入口，完成隔离回归，然后构建 NSIS 和 MSI。发布时使用新版本文件名，不覆盖历史安装器。

```powershell
cd app
npm test
npm run check:design
npm run tauri -- build
npm run release:r2 -- --version 0.1.6 --installer src-tauri/target/release/bundle/nsis/MollyCloud_0.1.6_x64-setup.exe --notes "更新说明"
```

最后一条命令默认只生成 `artifacts/update-dry-run/latest-0.1.6.json`，不会访问或修改存储桶。核对安装包、版本和本地清单后，在发布者的终端安全配置 `CLOUDFLARE_API_TOKEN` 环境变量，再给命令加 `--publish`。不要把 Token 直接写在命令行或提交到仓库。

发布脚本先检查线上版本，上传不可变的 `MollyCloud_0.1.6_x64-setup.exe` 并验证公共下载地址返回预期大小；全部成功后才替换 `latest.json`，最后重新读取公开清单核对 SHA-256。安装包设置长期缓存，清单设置 `no-store`。若公共域名未绑定或缓存配置错误，脚本会在更新清单之前停止。真实发布后还需手动核对浏览器下载、Windows 安装与升级保留用户数据。

清单示例：

```json
{
  "version": "0.1.6",
  "downloadUrl": "https://desktop.veriolink.com/MollyCloud_0.1.6_x64-setup.exe",
  "publishedAt": "2026-09-23T00:00:00.000Z",
  "sha256": "<64 位十六进制 SHA-256>",
  "sizeBytes": 12345678,
  "notes": "更新说明"
}
```

## 验证边界

- 启动只检查一次；有更高版本时登录后弹一次提示，关闭后仍可从顶部按钮重新打开。
- 下载域名必须是 `desktop.veriolink.com`；文件名必须与新版本匹配，无查询参数或跳转；清单必须包含有效 SHA-256 和非零文件大小。
- 清单是旧版本、返回 404、超时或格式错误时，登录和其他功能不受影响。
- 开发模式及浏览器设计预览不发布、不安装任何更新；旧的 `0.1.4` 安装包早于本轮界面改动，不能作为新版本发布。


## GitHub Releases 发布

GitHub 仓库为 https://github.com/ititrica/mollycloud-desktop，默认分支 `master`。
GitHub 安装包发行与 R2 应用内更新源是两个独立发布目标。

0.2.0 的本地产物位于 `artifacts/releases/0.2.0/`（不进入 Git 源码历史）。
源码提交、版本 tag 与 Release 指向同一个提交；发行附件包括 NSIS、MSI、
SHA256SUMS、第三方声明、更新说明和原始更新清单。

```powershell
gh release create v0.2.0 --repo ititrica/mollycloud-desktop --verify-tag --draft --title "MollyCloud v0.2.0" --notes-file "<发行说明路径>"
gh release upload v0.2.0 --repo ititrica/mollycloud-desktop "<NSIS 路径>" "<MSI 路径>" "<SHA256SUMS 路径>"
# 核对附件大小 / SHA-256 和源码提交后发布草稿。
gh release edit v0.2.0 --repo ititrica/mollycloud-desktop --draft=false --latest
```

先核对 README 下载链接、版本入口、许可证与源码提交范围，再提交和推送；
不把用户配置、密钥、构建缓存或测试日志提交到公开仓库。
新增版本使用新 tag 和附件名，不覆盖旧版本。用户明确要求同版本覆盖时，先备份被替换的平台 tag、Release 元数据和附件，再更新该平台源码、tag、包、清单与说明，并注明同版本不会触发自动更新。上传后的 API digest 应与本地 SHA-256 一致。

Release 中的 `latest.json` 保留桌面客户端已有协议及 R2 下载域名。
仅上传该文件到 GitHub 不会改动 `desktop.veriolink.com/latest.json`，
也不表示对应 R2 安装包已上传；发布 R2 仍使用本文件前述独立流程。

## Mac 先行发布与 Windows 文档同步

Mac 主开发分支为 `codex/macos-port`，Windows `master` 保留原基线，Windows 根据 Mac 改动独立移植、编译与实测。发布规则也写入根目录 [AGENTS.md](../AGENTS.md)，不能将失败的 `codex/windows-parity` 分支直接作为可用实现。

每次推送 Mac 源码或上传安装包必须同步维护：

- [Windows 更新记录](./Windows更新记录.md)：新增批次、当前 Mac 参考、具体变化、Windows 要做什么、测试与未验证项、发布状态，保留历史。
- [Windows 功能同步交接](./Windows功能同步交接.md)：更新完整目标、平台差异与验收；Windows 实际验证前状态保持待验证。

提交源码与这两份文档后再推送，并确保当次发行 tag 指向该提交。Mac tag 使用 `v<版本>-macos`，DMG 与 `latest-macos-<架构>.json` 保持独立；不能替换 Windows `v<版本>`、EXE 或 `latest.json`。Release 说明链接两份仓库文档，附件分别使用 `WINDOWS_SYNC_CHANGELOG.md` 和 `WINDOWS_SYNC_HANDOFF.md` 英文名，内容与仓库中文文档一致。

Mac 本地归档使用 `npm run release:macos`，见 [macOS 开发与打包](./macOS开发.md#本地发行归档)。上传顺序为 DMG、校验与验证摘要、文档和发行说明，最后替换该 Mac Release 的更新清单；完成后重新下载并核对大小 / 哈希，核对 tag 与源码提交，以及文档快照与 Git 源码一致。

`latest-macos-<架构>.json` 保留 `desktop.veriolink.com` 受信任域名，作为更新服务器的部署文件；本客户端不接受 GitHub 下载 URL 代替该域名。只上传 GitHub 时明确注明“更新域名未部署”，不能把新哈希的清单写到更新域名却仍保留旧包。部署到更新域名时先同步 DMG 并验证完整下载，再同步对应架构清单。
